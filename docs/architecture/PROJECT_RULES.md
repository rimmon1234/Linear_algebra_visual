# PROJECT_RULES.md

## Purpose

This document defines the engineering boundaries of the Interactive Linear Algebra Learning Platform. `AGENTS.md` defines agent behavior; this document defines architecture and code rules.

## 1. Architecture

Use these layers:

```text
Presentation/UI
      ↓
Feature orchestration
      ↓
Domain + Mathematics
      ↓
Infrastructure
```

Additional specialized subsystem:

```text
Math Engine → Visualization Model → Visualization Renderer
```

### Dependency rules

- `features/math/**` must not import React, Next.js UI components, Three.js, or React Three Fiber.
- `features/visualization/**` may import Three.js/R3F but must not own canonical mathematical algorithms.
- `content/**` is data/content only and must not perform database calls.
- UI components must not call external AI providers directly.
- UI components should not contain direct Supabase queries.
- Infrastructure code must not leak secrets to client components.
- Shared components must not contain large topic-specific `if/else` branches.

## 2. Source of Truth

There must be one canonical source for:

- curriculum structure,
- topic metadata,
- mathematical algorithms,
- visualization schema,
- numerical tolerances,
- API contracts.

Do not duplicate these across pages, components, prompts, or services.

## 3. Topic Modularity

A topic is content + configuration, not a custom application page.

Adding a topic should normally require:

1. Topic definition/content.
2. Registry entry.
3. Visualization preset(s).
4. Practice data.
5. Tests.

Removing a topic should normally archive it rather than breaking historical references.

## 4. Mathematics

Use deterministic computation whenever possible.

The canonical math engine owns:

- vector operations,
- matrix operations,
- RREF/rank,
- determinants/inverses,
- projections,
- basis operations,
- Gram-Schmidt,
- QR,
- eigenvalues/eigenvectors,
- SVD/pseudoinverse when supported.

UI code may request a result, but may not reimplement the same algorithm.

## 5. Numerical Correctness

Floating-point comparisons must use the policies in `NUMERICAL_POLICY.md`.

Never use exact equality for computed floating-point values when a tolerance is required.

Degenerate and invalid inputs must be handled intentionally.

## 6. Visualization

Visualizations must be mathematically truthful.

Every rendered object must originate from:

```text
validated visualization specification
```

Never execute arbitrary code generated by an LLM.

Prefer existing primitives before creating a new visualization type.

## 7. State

Use:

- React/local state for local UI state.
- Zustand for shared high-frequency interactive client state.
- TanStack Query for server/async state where useful.

Do not put every value into a global store.

## 8. Performance

- Keep render-loop updates out of unnecessary React state updates.
- Reuse Three.js geometries/materials.
- Lazy-load heavy visualization code when practical.
- Avoid unnecessary scene remounts.
- Test on lower-powered/mobile devices before declaring graphics work complete.

## 9. Validation

Validate untrusted data at boundaries using Zod or equivalent project-approved schemas.

Relevant boundaries include:

- API input,
- AI output,
- visualization specs,
- imported problem data,
- external service responses.

TypeScript types do not replace runtime validation.

## 10. API and Database

- Keep database access behind server-side services/repositories.
- Do not expose service-role credentials.
- Respect Row Level Security.
- Preserve API contracts unless a deliberate versioned change is documented.

## 11. Testing

A feature is incomplete without appropriate tests.

Minimum expectations:

- math logic → unit tests,
- cross-layer behavior → integration tests,
- user workflows → E2E tests,
- visualizer interactions → browser verification.

## 12. Refactoring

Do not mix unrelated refactors with feature work.

Before changing shared code:

1. Find all consumers.
2. Update types/contracts.
3. Update implementations.
4. Update tests.
5. Run relevant verification.

## 13. Accessibility and Responsive Behavior

The canvas is not the only source of understanding. Important values and explanations must remain available as text/UI.

All major controls must be usable with clear focus/labels, and layouts must adapt to mobile.

## 14. Error Handling

Expected failure states must be explicit:

- loading,
- invalid input,
- unsupported problem,
- numerical failure,
- AI failure,
- network failure,
- WebGL failure.

No user-facing `NaN`, `Infinity`, uncaught exception, or blank state.
